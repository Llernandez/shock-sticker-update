## 가설

### 인코딩

Delphi 2007은 유니코드 이전 버전이다. `string`이 `AnsiString`이고, 그 인코딩은
시스템 기본 코드페이지를 따른다. 한국어 윈도우에서는 CP949다.

이것이 사실이라면 두 가지 결과가 따라온다.

1. 파일 안의 한글은 CP949 바이트열이다. UTF-8이 아니다.
2. **다른 로케일의 윈도우에서 열면 깨진다.** "잘못된 포맷" 에러의 후보 중 하나다.

검증: `sskctl probe` 의 CP949 문자열 스캔에서 한글이 나오는가.

### 문자열 저장 방식

Delphi가 문자열을 스트림에 쓰는 흔한 형태는 셋이다.

| 방식 | 구조 | 최대 길이 |
|------|------|-----------|
| `ShortString` | 1바이트 길이 + 바이트열 | 255 |
| `AnsiString` | 4바이트 길이 + CP949 바이트열 | 2³¹ |
| `WideString` | 4바이트 길이(바이트 수) + UTF-16LE | 2³¹ |

`ShortString`이라면 **255바이트 = 한글 127자에서 메모가 잘린다.**
긴 메모에서 유실이 일어났다면 유력한 용의자다.

검증: `sskctl probe` 의 길이 접두사 후보에서 어느 폭이 규칙적인 간격을 보이는가.

### 직렬화 방식

Delphi가 `TStream.WriteComponent`로 객체를 통째로 저장했다면 파일은 `TPF0` 매직으로
시작한다. 이 경우 포맷 해석은 사실상 끝난 것이나 다름없다. DFM 바이너리 파서가
이미 여럿 존재한다.

검증: `sskctl probe` 의 매직 탐지.

### 날짜

`TDateTime`은 1899-12-30을 0으로 하는 8바이트 IEEE754 배정밀도 실수다.
1990~2050년은 대략 32000~55000 범위에 들어온다.

검증: `sskctl probe` 의 TDateTime 후보 스캔.
